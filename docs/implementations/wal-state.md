## 更新と参照

現在の`APP_HOSTS` / `APP_TRAFFIC_HOSTS`は`isucon-1`のみ。1つのGoプロセスが状態の更新を担当し、mutex内で検証・順序確定・WAL追記・メモリー更新を行う。WALへの書込みが失敗した場合、更新と通知を公開しない。プロセス間ではWALファイルの排他ロックで同じログへの二重書込みを防ぐ。この構造のまま複数アプリホストへ負荷分散することはできない。

- 座標APIは認証も含めてSQLを呼ばず、座標履歴、累計距離、最新位置、到着時のPICKUP / ARRIVEDを一つのレコードで確定する。
- 椅子の状態更新、活動状態、一括配車、評価後のCOMPLETED、通知送信済み記録もWALとメモリーで確定する。一括配車は上限64件と要求順を維持し、mainの改善を統合して全候補から迎車距離と乗車距離をモデル速度で割った移動時間の合計を最小化する一括割当を行う。位置・モデル不明の椅子は既知の候補の後に使う。モデル速度は起動・初期化時にDBから復元する。
- 通知はメモリーの全状態履歴から読み、flush成功後に送信済みをWALへ記録する。未送信イベントとLast-Event-ID以降を再送する。完了通知を消費するまで椅子を再割当しない。
- 近隣椅子、オーナーの距離一覧・売上、利用者のライド履歴、通知の椅子統計は同じ現在状態を参照する。
- 登録とライド作成・クーポン消費はDBで確定する。新しいライドとMATCHINGはcommit後にWALへ登録して公開する。決済情報の取得と決済呼出しは同期で行い、決済成功後に完了状態と椅子統計を確定する。

## 永続化と復元

WALの既定配置は、GoアプリのWorkingDirectoryから`../../state/state.wal`、現在のホスト配置では`/home/isucon/state/state.wal`。アプリ配布ディレクトリの外に置くので、通常のアプリ配布で削除されない。`ISURIDE_STATE_DIR`で配置を指定できる。

レコードはversion、世代、sequence、payload長、CRC32を持つ。受理した全座標と状態履歴を残し、リクエストごとのfsyncは行わない。500msごとと正常終了時に同期する。SIGQUIT / SIGTERM / SIGINTでHTTP処理を終了し、ログを同期して閉じる。

DB反映は100msごと、最大1,024レコード単位。最新値はbatch内でまとめ、座標・状態履歴は全件反映する。距離・椅子統計は加算ではなく確定済みの値をupsertし、履歴は同じ主キーで再試行する。`state_projection`の反映位置を同じtransactionで更新する。

起動時にDBのsnapshotと反映位置を読み、反映位置より後のWALを適用する。通知indexはreplay後に再構成する。利用者はライド要求順、椅子は割当・完了の順に並べ、作成が遅延した要求でも現在ライドと通知順序を維持する。末尾の不完全な追記だけを切り詰め、checksum・sequence異常やDB反映位置に必要なWALの欠損は起動エラーにする。

DB反映失敗時は未反映レコードを保持して再試行する。未反映レコードが32,768件に達した場合は、次の更新を追記前に拒否する。ライド作成のDB commit後にWAL登録が失敗した場合は、二重作成を避けるため、そのプロセスの新規更新を止め、再起動でDBとWALから復元する。

初期化は通常リクエストとDB反映を止め、既存SSEを終了し、公式SQLでDBを再作成した後にログ世代と反映位置を更新する。初期状態をロードし、旧世代のログを破棄する。ログは初期化まで保持する。

## FAIL後の修正

RUN `20261011-050820`の結果は登録500が211件、ライド作成500が2件、近隣椅子の利用中判定が2件。公式手順のワーニング200件打ち切りに達した。実DBのクーポン索引は`PRIMARY(user_id, code)`のみで、招待登録の`WHERE code = ? FOR UPDATE`が全表走査だった。保存されたロック待ちとデッドロックログから、登録とクーポン消費の競合を確認した。

クーポン更新は招待元ユーザーのmutexとライド作成のmutexを共用し、SQL transactionを開く前に取得する。招待上限確認は`code`索引による非ロックCOUNTに変更し、ライド作成のクーポン検索もSQL range lockを除いた。招待検索は登録時と復元時に作るメモリーindexを使う。招待上限3件・報酬額・新規登録クーポンを維持し、同一ミリ秒でも報酬キーが衝突しないようULIDを使う。`idx_coupons_code`は初期化schemaと起動時の不足索引作成に含める。既存の単一Goプロセスという前提を使う。

近隣椅子の2件はWAL上のCOMPLETEDから約1ms・6ms後に報告されていた。評価応答のflush完了までは椅子を近隣一覧に公開せず、flush終了後100msの猶予を設けた。同期完了・受信確認をクライアントから得るAPIはないため、この猶予は観測された応答順序の競合への対策であり、クライアント受信の保証ではない。通常の応答失敗でも保留を解除して猶予へ移り、再起動時は永続化したCOMPLETEDの時刻から猶予を復元する。完了状態・履歴・統計は先にWALへ確定し、配車と座標応答には猶予待ちを入れない。

追加テストでは96件の並行招待登録と12件の同時クーポン消費、招待上限・報酬数・索引追加・招待検索復元、評価応答flushを止めた状態での近隣取得、猶予の1ms・6ms・境界時刻、再起動後の再公開を確認した。`task build`（Linux/amd64）、`task test-app`、`task check-chair-distance`は通過。修正時点ではユーザー指示によりデプロイを保留し、その後の再デプロイ指示で下記のmain統合と合わせて反映した。ベンチ合格は未確認。
