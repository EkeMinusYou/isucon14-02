# ベンチマーカーの振る舞い

ベンチマーカーがどう動き、何を判定するかについて、観測から分かったことを残す。
ユーザー・椅子・オーナーが何を見てどのAPIをどの順・条件で呼ぶか、警告・失敗が出る条件、
評価や人数・椅子の増減の条件などが対象。こちらの実装の状態（CPU、待ち、処理量）は書かない。

ベンチマーカーのソースは読まない。参加者向けベンチ出力、アクセスログ、ユーザー遷移、
アプリ側の記録など、許可された観測から導く。

## 書き方

- 1項目は見出し1つと、日時付きの箇条書き。最初の行に確度（確定・有力・仮説）と根拠を書く。
- 根拠には、比較したRUNと値、再実行できるクエリやファイルの場所を書く。
- 設計への影響（避けるべき変更、効く変更）を書く。
- 追記と訂正だけで更新し、全体を書き直さない。確度の変更や反証は、その項目に日時付きの行を足す。

```markdown
### <ベンチマーカーの振る舞いを1文で>
- YYYY-MM-DD HH:MM 仮説：<内容>。根拠：<RUN・値・クエリ>。影響：<設計への影響>
- YYYY-MM-DD HH:MM 確定に変更：<追加の根拠>
```

## 項目

### ユーザーは通知SSEを常に開いておき、終わるとすぐ、評価と並行して接続し直す
- 2026-10-11 22:20 有力：根拠：SSEをARRIVEDでも終えた220414では、評価が新しい接続で来た数が11,764→1,596に減った一方、通知が新しい接続で来た数が0→10,067に増え、新しい接続の総数は22,648→22,363でほぼ同じ（`http_traffic`の`new_connections`をroute別に214202と比較）。生ログ（`runs/20261011-220414/raw/access-*.log.zst`）を`session_id`で並べると、SSEが終わった約30ms後に、評価は空いた接続で、通知は新しい接続で同時に送られている。影響：SSEをどこで終えても、評価のまわりで必要な接続は2本のままで、ハンドシェイクの総数は減らない。ARRIVEDで終えると通知のリクエストが+63%になる。

### ユーザーが待機中の接続を再利用するのは、空き時間が約10秒未満のときだけ
- 2026-10-11 22:00 有力：根拠：214202で、前回の評価の接続を再利用した評価4,614件は、前の評価からの空き時間が中央値3.7秒・最大9.99秒。新しい接続で来た5,990件は中央値12.6秒・90%値14.0秒（生ログを`session_id`と接続番号で並べて計算）。nginxの`keepalive_timeout`は未設定（既定75秒）なので、接続を捨てているのはクライアント側と推定。影響：ライドの周期が10秒を超えるユーザーは、評価のたびにTLSハンドシェイクが起きる。こちらからは延ばせない。
