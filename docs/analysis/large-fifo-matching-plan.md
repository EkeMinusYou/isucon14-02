## 構造と正当性

`runtime_matching.go` で、FIFO先頭 `min(待機数, 空き椅子数, 256)` 件と全空き椅子の
位置・モデル速度・初期化世代を値としてコピーする。コピー時だけ `s.mu.RLock` を使い、
候補ソート・抽出・solverは共通状態ロック外で実行する。
別の `matchingMu` は配車呼出し同士だけを直列化し、重複計算を避ける。
座標更新・通知ACK・activityはこのplanner用mutexを取得しない。

従来の候補unionに対する密なHungarian費用行列を廃止し、ライドごとの上位n台を辺として残す
疎な二部グラフで、ポテンシャルとDijkstra法による最小費用の増加路をn回求める。
逆辺を通じて計画全体の割当を組み替えられる。隣接リストは次数から事前確保し、
探索heapも型付きにして辺ごとのinterface確保を避ける。
旧Hungarian法は比較用の `_test.go` だけに置き、アプリbinaryには含めない。

費用は `(迎車マンハッタン距離 + 乗車マンハッタン距離) / モデル速度`、単位は推定秒。
各ライドの上位n台のうち他の割当が使えるのは最大n−1台なので、候補外の椅子を使う解は
候補内の未使用椅子へ費用を増やさず置換できる。この抽出には最適解が残る。
座標や速度が不明な椅子も残し、有限penaltyを `(n+1)*(最大既知費用+1)` として、
未知椅子の使用台数を先に最小化する。未知を近い椅子・所要時間0として扱わない。
未知が必要な場合は全既知椅子が各行の候補に残るため、このpenaltyで既知費用全体を覆える。

近似的なtop-k、空間索引、速度別索引は採用していない。選択されたFIFO集合に対して
スナップショット費用を最小化する。float64の丸め誤差はあり、増加路の理論上非負の
縮約費用が負へ丸められる場合は0へ補正する。小規模の独立全探索と大規模の従来solver比較で
費用を確認した。256件より後のライドは計画に含まず、全待機列に対する最適解ではない。

n<=256、全空き椅子数C、assignment辺E<=n²、頂点V<=n+min(C,n²)+2。
候補抽出は `O(n*C*log(n))`、solverは `O(n*(E+V)*log(V))`、
全体のメモリは `O(n²+C)`。従来の密な行列に対する `O(n²*候補union台数)` を
そのまま大きくする方式ではない。ただし少数・共有候補が多い場合は従来Hungarian法のほうが速い。
上限256件は64件の境界を越え、局所計算で時間・メモリを確認した暫定値。
空き椅子が64台以下なら64件以下を計画し、負荷や長距離を理由に古い依頼を飛ばさない。

確定時は `s.mu.Lock` で以下を一括検証する。

1. stateがready、WALが利用可能、初期化世代が同じ。
2. 全計画ライドが現存して未割当、かつ現在もFIFOの同じ先頭集合。
   SQL作成の遅着で古い依頼が前に挿入された場合も検出する。
3. 全採用椅子が現存してactive、未完了ライドなし、全椅子通知ACK済み。

競合した計画は部分確定せず、同じ世代ならスナップショットから最大3回計算する。
それでも競合が続けば次の外部matcher呼出しへ残し、旧世代なら破棄する。
継続的なactivity変更などがある場合の待ち時間上限は保証しない。
正常な依頼列ではFIFOの先頭だけを選ぶため、長距離の古い依頼を短距離へ置換して飢餓を起こさない。

座標更新だけでは再計画しない。高頻度の座標更新で確定が永久に失敗することを避けるためで、
計算開始後の移動によって確定時の費用最適性は変わり得る。既存の推定迎車メトリクスは
確定時の最新位置・速度で計算し、計画時の古い位置を測定値として公開しない。

最大256件を既存の単一 `stateRecord.Rides` に入れ、WAL append成功後に既存apply処理で
状態・通知queueを公開し、既存のSSE wakeを送る。WAL失敗では割当・計測・通知を公開しない。
通常再起動のWAL復元と、全通知ACK後に再利用する既存の規則を維持する。
SQL投影は戻しておらず、SQLの初期状態・作成済みrideとWALを正本として使う。

## 同じ集合での品質比較

競技ベンチマーカーの実行・ソース解析はしていない。
`matching_comparison_test.go` は同じFIFOライドと同じ全空き椅子から、
従来の64件ごとの最適割当で消費した椅子を後続から除く方法と、今回の一括計画を比較する。
両方式とも全件を割り当てるので、外部呼出し回数や割当数増加の影響を含まない。
以下は全ライドの推定秒の合計で、実測秒・RUN得点ではない。

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 128件／128台、境界をまたぐ迎車競合 | 448.000 | 192.000 | 64.000 | 64.000 | 512.000 | 256.000 |
| 128件／128台、後続64件が長距離・速度差あり | 0 | 0 | 64,006.400 | 6,464.000 | 64,006.400 | 6,464.000 |

## 計算費用と検証

ローカルはDarwin/arm64、Apple M1、`-benchtime=10x -count=1`。
各値は計画1回の平均wall timeと累計allocated bytesで、サーバーCPU秒・peak RSSではない。
従来側は同じ件数を64件ずつ処理する全solver時間の合計。

| 件数／候補1,024台 | 従来64件ずつ | 新計画 | 従来allocated bytes | 新allocated bytes |
| --- | ---: | ---: | ---: | ---: |
| 64 | 1.882ms | 3.401ms | 476,948 | 491,456 |
| 128 | 3.744ms | 16.494ms | 903,723 | 1,670,315 |
| 256 | 7.272ms | 79.275ms | 1,713,332 | 6,037,527 |

256件では約10.9倍の計算時間が必要だが、その長い計算中は共通状態ロックを取得しない。
次数による事前確保前は約15.5MB/planだった確保量を約6.0MBへ削減した。
1回で最大256件を確定するため、WAL/apply・既存計測・通知のロック保持時間も従来の
64件1回より増える。solver時間の短縮やサーバーの座標API改善をローカル結果だけで断定しない。

実行した確認:

```sh
cd webapp/go
go test ./...
go test -run 'TestMatchingAcross64Boundary|TestMatchingLargePlanQuality' -v
go test -run '^$' -bench BenchmarkLocalMatchingComparison -benchtime=10x -count=1
go test -race ./...
cd ../..
task build TARGET_OS=linux TARGET_ARCH=amd64
git diff --check
```

上記は成功。race付き全Goテストは11.859秒。
MySQLを必要とする既存integration testはDSN未指定のためskipし、サーバーDBは操作していない。
新規テストで初期化世代・FIFO遅着・非活動・未完了・全通知ACK条件・既割当の再検証、
同一計画の同時確定がWAL1件だけになること、計算と座標書込みの並行、最新位置での推定迎車、
256件上限と未知椅子fallback、WALをclose/reopenしての割当・通知待ちの復元を確認した。
既存のWAL失敗時の未公開・SSE wakeなし、FIFO・長距離優先、全探索比較も通っている。

## 既存計測の契約整合と次のRUN

カウンター・ログは追加しない。既存の `pickup_b9_64` / `_unknown` を
`pickup_b9_plus` / `_unknown` に改名し、9件以上の計画を表す。
`ride_metrics_version` は2。既存 `dispatch_batch` の境界1／8／32／64は維持し、
64件超は `_inf - _b3` で数える。件数合計は `_sum`、平均バッチサイズは `_sum / _n`。

競技固有の分析schemaだけは、この計測契約に必要な整合として更新した。
`tools/contest/analysis-schema/ride-metrics.sql` はv1の旧名・cohort9_64とv2の新名・cohort9_plusを読み、
versionが変わる差分間隔を無効にする。v1互換の定義は保存RUNの解釈用で、
アプリの旧配車コードや互換運転フラグではない。
既存分析DBや保存RUN成果物は書き換えていない。将来のユーザーRUNを通常の分析経路で取り込む際に
このschemaを使う。DuckDBのin-memory合成4サンプルでv1の64件、v2の256件、
version境界のdelta欠落、64件超の既存infinity bucketを確認した。

今後のユーザーRUNはこのcommit単独でPASS／scoreを確認する。
同じ窓で配車件数/秒、バッチ件数・件数分布、FIFO待ち/oldest、推定迎車、迎車・移動不満、
低評価離脱、完了数、椅子成長、Go CPU秒と容量、座標API遅延を比較する。
既存profileではsnapshot／候補抽出／solver／commitとmutex待ちを確認できる。
新たな競合回数カウンターは追加していないので、RUNから再計画回数を直接集計はできない。
競合条件はローカルテストで確認し、実負荷の再計画費用は既存profileとCPU・配車待ちで評価する。

一括確定で1呼出しの上限が64→256となるため、RUNの変化には割当品質と処理量増の両方が入る。
品質だけの根拠は上の同じ集合のsolver比較に限定し、配車件数増を品質向上の証拠としない。
v1のpickup9_64とv2のpickup9_plusは母数も異なり、平均値だけで品質改善と判断しない。
現行メトリクスだけでは65件以上のpickupを別コホートへ分離できない。
将来RUNではバッチ分布・同じ候補供給/待機状況・時間窓を併記し、実効回転と得点への合算効果を判断する。
欠損差分は0に埋めず、有効観測秒数と件数を示す。

案②単独の増点は未確定で、2倍級の根拠はない。費用が減っても迎車距離の加点が減る可能性、
CPU／GC増加、候補の使い切り、座標の計画後変化、大きな確定のロック時間がある。
これらを含む得点と正当性の判断には、許可された将来のユーザーRUNが必要となる。
