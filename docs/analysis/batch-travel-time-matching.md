# 迎車・乗車時間による一括配車

会話ログ `docs/conversation/20261011-040540_01a12734-c490-7542-8396-036c0f2fc959.md`
の改善案2を、mon worktreeにローカル実装した。対象はGoの内部配車処理。
配布を行う場合の対象はTaskfileのAPP_HOSTSである `isucon-1` の `isuride-go`。
今回はデプロイ、サービス操作、競技ベンチ実行を行っていない。

## 割当方針

- 古い未割当ライドから最大64件を読み、空き椅子が少ない場合も古い依頼を優先する。
- 費用は `(現在位置→乗車位置のマンハッタン距離 + 乗車位置→目的地のマンハッタン距離) / モデル速度`。
- 今回割り当てる件数をNとし、各ライドの費用が小さいN脚を候補として残す。
  候補の和集合は最大N²脚。この集合上で矩形のHungarian法を使い、合計費用を最小化する。
- N脚のうち他のライドが使えるのは最大N−1脚なので、候補外の椅子を使う割当は
  空いている候補へ費用を増やさず置き換えられる。この絞り込みは現在の目的関数の最適解を残す。
- 乗車距離が長いことを理由に依頼を候補から外さず、行き先・料金計算・状態遷移は維持する。
- 位置は既存の `chair_distance_totals`、速度は `chair_models` を参照する。
  main取り込み後は、位置未登録、モデル不明、速度が正でない椅子も最終候補として残す。
  不明な椅子の使用数を先に最小化し、そのうえで既知の推定時間を最小化する。
  不明な費用は一括割当の既知費用合計より大きい有限値に置き換え、
  全椅子の情報が不明な場合も依頼を放置せず割り当てる。

`matching.go` の計算はDB・通知へ依存しない。状態管理側はスナップショットを渡し、
返されたライド・椅子のインデックスを検証して適用できる。

## 適用時の条件と増える仕事

待機ライドの行ロック、椅子ID順の行ロック、READ COMMITTEDでの空き状態再確認を維持する。
前ライドが完了し、椅子宛の全通知が送信済みである椅子だけを利用する。
ロック後に位置・速度も読み直し、利用可能な椅子の範囲で再計算する。
利用可能数が減った場合も古いライドへ割り当てる。
一括UPDATEのcommit後にSSEを起こし、受理済み割当は従来どおりDBへ永続化する。

SQL往復数とロック対象数は従来と同じ。空き椅子取得に現在位置・モデルのJOINと
座標・速度の転送が増える。候補選択は O(N × 空き椅子数 × log N)、
割当は O(N² × 候補数)、費用行列は O(N × 候補数)。
椅子ロックは候補全体ではなく実際に選んだ最大64脚だけに取る。
